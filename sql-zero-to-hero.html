Level 0Set up a playground (5 minutes)

You learn SQL by typing it. Reading alone is not enough. Pick a place to run queries:

  • DB Fiddle: choose "PostgreSQL" at the top, paste the script below into the left panel, and write your queries in the right panel. Nothing to install, no account needed.
  • Any PostgreSQL database you can use: a local install, or a free cloud database. Use a separate scratch database, never a production or reporting database.

Paste this script once. It builds a small accounts-payable system: cost centres spend money, vendors send invoices, and the company records payments against those invoices. All amounts are in EUR. Every example and exercise below uses these tables.

CREATE TABLE cost_centers (
  id        INT PRIMARY KEY,
  name      TEXT NOT NULL,
  parent_id INT REFERENCES cost_centers(id)
);
CREATE TABLE vendors (
  id      INT PRIMARY KEY,
  name    TEXT NOT NULL UNIQUE,
  country TEXT
);
CREATE TABLE invoices (
  id             INT PRIMARY KEY,
  vendor_id      INT NOT NULL REFERENCES vendors(id),
  cost_center_id INT REFERENCES cost_centers(id),
  invoice_date   DATE NOT NULL,
  due_date       DATE NOT NULL,
  amount         NUMERIC(12,2) NOT NULL
);
CREATE TABLE payments (
  id         INT PRIMARY KEY,
  invoice_id INT NOT NULL REFERENCES invoices(id),
  paid_on    DATE NOT NULL,
  amount     NUMERIC(12,2) NOT NULL
);

Level 1What a database is

Why

A spreadsheet breaks down once several people and programs edit it at the same time, when it holds millions of rows, or when the data must follow rules (like "every invoice belongs to a real vendor"). An ERP or accounting system stores its data in a relational database, and SQL (Structured Query Language) is the language for asking it questions directly, without waiting for someone to build a report.

The vocabulary you need:

WordMeansSpreadsheet equivalent
TableOne kind of thing (invoices)One sheet
Row (record)One instance (invoice 104)One line
Column (field)One property (amount), with a fixed typeOne column
Primary keyThe column that identifies each row and never repeats (invoices.id)An invoice number you never reuse
Foreign keyA column pointing to another table's primary key (invoices.vendor_id → vendors.id)A VLOOKUP that the database enforces

How our four tables link

cost_centers.id  ◄── invoices.cost_center_id
cost_centers.id  ◄── cost_centers.parent_id   (a centre's parent)
vendors.id       ◄── invoices.vendor_id
invoices.id      ◄── payments.invoice_id

Read each arrow as "points to". One vendor has many invoices; one invoice has zero, one or many payments. The foreign key always sits on the "many" side.

SQL is declarative: you describe what you want ("unpaid invoices from Swedish vendors"), and the database works out how to fetch it. You never write loops.

SQL commands fall into four families:

  • Query: SELECT reads data (about 80% of an analyst's time).
  • Change data: INSERT, UPDATE, DELETE.
  • Define structure: CREATE, ALTER, DROP.
  • Control: BEGIN/COMMIT (transactions), GRANT (permissions).
Say it like this

"A relational database stores data in tables linked by keys, and SQL is the declarative language for reading and changing that data."

Level 2Your first SELECT

Why

Every report, reconciliation and dashboard starts by reading rows. SELECT is the one command you will type thousands of times.

SELECT id, invoice_date, amount
FROM invoices;

Read it as: "From the invoices table, give me the id, date and amount columns." The semicolon ends the statement. Keywords are not case-sensitive, but writing them in CAPITALS is the usual convention and makes queries easier to scan.

Compute and rename

SELECT id,
       amount,
       amount * 0.20            AS vat,
       amount * 1.20            AS gross,
       due_date - invoice_date  AS payment_terms_days
FROM invoices;

AS gives a column a new name in the result (an alias). Subtracting one date from another gives the number of days between them.

Remove duplicates

SELECT DISTINCT vendor_id FROM invoices;  -- 1, 2, 3, 4
Trap

SELECT * is fine for a quick look. In saved reports, name the columns: the query is faster, and it does not break when someone adds a column.

List every vendor's name and country.
SELECT name, country FROM vendors;
Show each invoice's id and amount after a 2% early-payment discount, as discounted.
SELECT id, amount * 0.98 AS discounted FROM invoices;

Level 3Filtering with WHERE

Why

You almost never want every row. WHERE keeps only the rows for which a condition is true, and the database can use indexes to skip the rest without reading them.

SELECT id, amount
FROM invoices
WHERE amount >= 5000;

Combine conditions

WHERE vendor_id = 2 AND amount < 5000        -- both must be true
WHERE vendor_id = 1 OR vendor_id = 3         -- at least one
WHERE vendor_id IN (1, 3)                   -- same, shorter
WHERE amount BETWEEN 1000 AND 5000          -- inclusive
WHERE due_date < '2024-04-01'               -- dates compare too
WHERE name LIKE '%Media'                     -- ends with "Media"
WHERE name ILIKE '%cloud%'                   -- contains, any case
WHERE cost_center_id IS NULL               -- not coded yet
Trap: AND before OR

WHERE vendor_id = 1 OR vendor_id = 2 AND amount > 5000 means 1 OR (2 AND >5000), because AND is evaluated first. Whenever you mix the two, add brackets.

Trap: month-end filters

For "all invoices in March", use a half-open range: invoice_date >= '2024-03-01' AND invoice_date < '2024-04-01'. It works for dates and timestamps alike, and you never have to know whether the month has 30 or 31 days.

Invoices issued in March 2024.
SELECT id, invoice_date, amount FROM invoices
WHERE invoice_date >= '2024-03-01' AND invoice_date < '2024-04-01';

103 and 104.

Invoices from vendors 1 or 2 above 5000.
SELECT id, amount FROM invoices
WHERE vendor_id IN (1, 2) AND amount > 5000;

101 and 106.

Which invoices still need a cost centre?
SELECT id FROM invoices WHERE cost_center_id IS NULL;   -- 105

Level 4Sorting and limiting

Why

A table has no built-in order. If you want "the 3 largest invoices" or "the oldest due first", you must ask for it with ORDER BY. Otherwise the order can change between two runs of the same query.

SELECT id, amount
FROM invoices
ORDER BY amount DESC, id   -- tie-break by id
LIMIT 3;

OFFSET 3 skips the first 3 rows, which gives you page 2. Always add a tie-breaker (like id): invoices 102 and 103 have the same amount, and without one, their order is not guaranteed.

The two invoices due first.
SELECT id, due_date FROM invoices
ORDER BY due_date LIMIT 2;

101 and 102.

Level 5Aggregates: summarising rows

Why

Finance questions start with "how much?", "how many?" and "on average?". Aggregate functions turn many rows into one number.

SELECT COUNT(*)                  AS invoices,     -- 6
       COUNT(cost_center_id)     AS coded,        -- 5
       COUNT(DISTINCT vendor_id)  AS vendors,      -- 4
       SUM(amount)                AS total_spend,  -- 44950
       ROUND(AVG(amount), 2)      AS avg_invoice,  -- 7491.67
       MIN(invoice_date)          AS first_invoice
FROM invoices;

COUNT(cost_center_id) gives 5, not 6, because aggregates skip NULLs. Only COUNT(*) counts every row.

Total paid out so far.
SELECT SUM(amount) FROM payments;   -- 27000

Level 6GROUP BY and HAVING

Why

"Total spend" is one number. "Spend per vendor" is one number per group. GROUP BY splits the rows into piles, and each aggregate then runs once per pile. This is the SQL version of a pivot table.

SELECT vendor_id,
       COUNT(*)    AS invoices,
       SUM(amount) AS spend
FROM invoices
GROUP BY vendor_id
ORDER BY spend DESC;
-- 1: 2 / 27000 · 2: 2 / 9000 · 3: 1 / 8000 · 4: 1 / 950

If you group by cost_center_id, NULL forms its own group, so invoice 105 appears as a row with cost centre NULL.

WHERE vs HAVING

WHERE filters rows before they are grouped. HAVING filters groups after the aggregates are calculated.

SELECT vendor_id, SUM(amount) AS spend
FROM invoices
WHERE invoice_date >= '2024-02-01'   -- ignore January first
GROUP BY vendor_id
HAVING SUM(amount) > 5000;          -- big vendors only

The rule that explains every GROUP BY error

After grouping, a group has one value for vendor_id but several due dates. Asking for due_date is therefore ambiguous. Every selected column must be grouped or aggregated.

The order the database really runs

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This is why an alias created in SELECT works in ORDER BY but not in WHERE: WHERE runs before SELECT has created it.

Spend per cost centre id.
SELECT cost_center_id, SUM(amount) AS spend
FROM invoices GROUP BY cost_center_id;

2: 27000 · 4: 9000 · 3: 8000 · NULL: 950.

Vendors (by id) with more than one invoice.
SELECT vendor_id, COUNT(*)
FROM invoices
GROUP BY vendor_id
HAVING COUNT(*) > 1;

Vendors 1 and 2.

Spend per month.
SELECT TO_CHAR(invoice_date, 'YYYY-MM') AS period, SUM(amount)
FROM invoices GROUP BY period ORDER BY period;

2024-01: 12000 · 02: 4500 · 03: 12500 · 04: 15950. Postgres allows the alias in GROUP BY; not every database does.

Level 7JOINs and foreign keys

Why

Good design stores each fact once. The vendor's name lives only in vendors; each invoice stores just the vendor_id foreign key. If the vendor changes its name, you change one row. A JOIN follows the foreign key to put the pieces back together when you read.

SELECT i.id, v.name AS vendor, i.amount
FROM invoices i
JOIN vendors v ON v.id = i.vendor_id;

Think of it this way: for each invoice row, find the vendor rows where the ON condition is true, and glue the two together. i and v are short aliases; they are required when both tables have a column with the same name (here, id and amount).

Rule of thumb

The ON clause almost always reads primary key = foreign key: v.id = i.vendor_id, c.id = i.cost_center_id, i.id = p.invoice_id. If you can't name the foreign key you are following, stop and check the design.

The four joins, using invoices ⟷ cost_centers

JoinRowsWhat happens to the gaps
INNER JOIN5Invoice 105 is dropped (no cost centre)
LEFT JOIN6Invoice 105 is kept, with cost centre NULL
RIGHT JOIN7Head Office and Legal appear, with invoice NULL
FULL JOIN8All of the above

Decide which one you need by asking: "Which table must lose no rows?" Put that table first and use LEFT JOIN. An INNER JOIN in a spend report silently hides uncoded invoices, which is exactly the money a controller wants to see.

Join three or more tables

SELECT i.id, v.name AS vendor, v.country,
       COALESCE(c.name, 'Uncoded') AS cost_center, i.amount
FROM invoices i
JOIN      vendors v      ON v.id = i.vendor_id
LEFT JOIN cost_centers c ON c.id = i.cost_center_id;

Find what is missing (anti-join)

-- vendors on file who never invoiced
SELECT v.name
FROM vendors v
LEFT JOIN invoices i ON i.vendor_id = v.id
WHERE i.id IS NULL;          -- Orbit Consulting

Self join: a table joined to itself

cost_centers.parent_id is a foreign key to the same table. To show each centre with its parent, join the table to itself under two aliases:

SELECT c.name, p.name AS parent
FROM cost_centers c
LEFT JOIN cost_centers p ON p.id = c.parent_id;
-- IT → Operations, Operations → Head Office, Head Office → NULL …
Trap 1: WHERE breaks a LEFT JOIN

LEFT JOIN payments p ON … WHERE p.paid_on >= '2024-04-01' removes every invoice without a payment, because its p.paid_on is NULL. To keep them, move the condition into the join: ON p.invoice_id = i.id AND p.paid_on >= '2024-04-01'.

Trap 2: inflated totals (fan-out)

Invoice 106 has 2 payments. Join invoices to payments and the 15 000 invoice appears twice, so SUM(i.amount) returns 59 950 instead of 44 950. This is the most common cause of wrong numbers in finance reports. Fix it by summing payments per invoice first (Level 9), then joining.

Spend per cost centre name, including centres with 0 spend.
SELECT c.name, COALESCE(SUM(i.amount), 0) AS spend
FROM cost_centers c
LEFT JOIN invoices i ON i.cost_center_id = c.id
GROUP BY c.name
ORDER BY spend DESC;

Operations 27000 · IT 9000 · Marketing 8000 · Head Office 0 · Legal 0. Uncoded invoice 105 is not here; it has no cost centre to belong to.

Spend per vendor country.
SELECT v.country, SUM(i.amount) AS spend
FROM invoices i
JOIN vendors v ON v.id = i.vendor_id
GROUP BY v.country
ORDER BY spend DESC;

Morocco 27000 · Sweden 9000 · France 8000 · UAE 950.

Every payment with its vendor name (follow two foreign keys).
SELECT p.id, p.paid_on, p.amount, v.name AS vendor
FROM payments p
JOIN invoices i ON i.id = p.invoice_id
JOIN vendors  v ON v.id = i.vendor_id;

Level 8NULL and CASE

Why

NULL means "unknown", not zero and not empty text. Comparing anything with an unknown gives "unknown", which is why = NULL never matches a row. In finance, a missing payment is a NULL after a LEFT JOIN, so most wrong balances start here.

ExpressionResult
NULL = NULLNULL (not true!)
4500 - NULLNULL: an unpaid invoice's balance disappears
x IS NULLtrue / false: the correct test
COALESCE(paid, 0)paid, or 0 if paid is NULL
NULLIF(budget, 0)NULL when budget = 0, which makes actual / NULLIF(budget, 0) safe
The NOT IN trap

WHERE id NOT IN (SELECT parent_id FROM cost_centers) should list the centres that have no children, but it returns nothing. Head Office's parent_id is NULL, and "is 3 different from unknown?" has no answer. Use NOT EXISTS, which handles NULLs correctly.

CASE: if/else inside a query

SELECT id, amount,
  CASE
    WHEN amount >= 10000 THEN 'CFO approval'
    WHEN amount >= 5000  THEN 'manager approval'
    ELSE 'auto-approve'
  END AS approval_level
FROM invoices;

Combine CASE with an aggregate to build a pivot: one row, one column per category.

SELECT
  SUM(amount) FILTER (WHERE invoice_date < '2024-04-01') AS q1,
  SUM(CASE WHEN invoice_date >= '2024-04-01' THEN amount ELSE 0 END) AS q2
FROM invoices;     -- q1 29000 · q2 15950
Count invoices per approval level (use the CASE above).
SELECT CASE WHEN amount >= 10000 THEN 'CFO approval'
            WHEN amount >= 5000  THEN 'manager approval'
            ELSE 'auto-approve' END AS level,
       COUNT(*), SUM(amount)
FROM invoices GROUP BY level;

CFO 2 (27000) · manager 1 (8000) · auto 3 (9950).

Cost centres that have no child centres, written correctly.
SELECT c.name FROM cost_centers c
WHERE NOT EXISTS (SELECT 1 FROM cost_centers k WHERE k.parent_id = c.id);

Marketing, IT, Legal.

Level 9Subqueries and CTEs

Why

Many finance questions need two steps: "which invoices are above the average?" needs the average first, and "what is still open?" needs the payments summed first. A subquery is a query inside a query. A CTE (WITH) gives that inner query a name, so you can read the steps from top to bottom, like a recipe.

Subquery that returns one value

SELECT id, amount FROM invoices
WHERE amount > (SELECT AVG(amount) FROM invoices);   -- 101, 104, 106

Subquery that returns a list

SELECT name FROM vendors
WHERE id IN (SELECT vendor_id FROM invoices WHERE amount > 10000);

EXISTS: "is there at least one?"

SELECT i.id FROM invoices i
WHERE NOT EXISTS (
  SELECT 1 FROM payments p WHERE p.invoice_id = i.id
);   -- never paid at all: 103, 105

CTE: the open-balance report

WITH paid AS (
  SELECT invoice_id, SUM(amount) AS paid
  FROM payments GROUP BY invoice_id        -- ONE row per invoice
)
SELECT i.id, v.name AS vendor, i.amount,
       COALESCE(p.paid, 0)            AS paid,
       i.amount - COALESCE(p.paid, 0) AS open_balance
FROM invoices i
JOIN      vendors v ON v.id = i.vendor_id
LEFT JOIN paid p    ON p.invoice_id = i.id
ORDER BY open_balance DESC;
-- 106: 7500 · 104: 5000 · 103: 4500 · 105: 950 · 101, 102: 0

This is the fix for the fan-out trap in Level 7: payments are summed to one row per invoice before the join, so no invoice is counted twice. Total open: 17 950.

Habit

When a query feels hard, write it as a chain of CTEs: one small, testable step each. Run each step on its own (SELECT * FROM paid) and check it against a number you trust before you add the next one. Reconcile, then build.

Open balance per vendor (vendor name and total still owed).
WITH paid AS (
  SELECT invoice_id, SUM(amount) AS paid
  FROM payments GROUP BY invoice_id
)
SELECT v.name, SUM(i.amount - COALESCE(p.paid, 0)) AS owed
FROM invoices i
JOIN vendors v ON v.id = i.vendor_id
LEFT JOIN paid p ON p.invoice_id = i.id
GROUP BY v.name
ORDER BY owed DESC;

Atlas Logistics 7500 · Lumen Media 5000 · Nordic Cloud 4500 · Gulf Office Supply 950.

Invoices above their own vendor's average invoice.
WITH vendor_avg AS (
  SELECT vendor_id, AVG(amount) AS avg_amount
  FROM invoices GROUP BY vendor_id
)
SELECT i.id, i.amount, a.avg_amount
FROM invoices i JOIN vendor_avg a ON a.vendor_id = i.vendor_id
WHERE i.amount > a.avg_amount;

Only 106 (15000 vs Atlas's average of 13500).

Level 10Changing data

Why

Reading is safe. Writing is permanent, and in finance it is audited. Even if you mostly report, you need to understand these commands to load data, fix coding errors, and read what your systems do behind the scenes.

INSERT INTO vendors (id, name, country) VALUES (6, 'Delta Print', 'Spain');

UPDATE invoices
SET cost_center_id = 3
WHERE id = 105
RETURNING id, cost_center_id;      -- Postgres: show the result

DELETE FROM vendors WHERE id = 6;

The safe workflow

  1. Write the WHERE as a SELECT first, and check exactly which rows come back.
  2. Wrap the change in BEGIN; … check with a SELECT … then COMMIT; or ROLLBACK;.
  3. Never paste user input into SQL text. Use parameters (WHERE id = $1). Pasting the text directly is how SQL injection happens.

Upsert: insert, or update if it already exists

INSERT INTO vendors (id, name, country) VALUES (5, 'Orbit Consulting LLC', 'USA')
ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name;
Foreign keys protect you

Try DELETE FROM vendors WHERE id = 1;. It fails, because invoices still reference Atlas Logistics. Try INSERT INTO invoices VALUES (107, 99, NULL, '2024-05-01', '2024-05-31', 100);. It fails too: vendor 99 does not exist. That error is the database refusing to create an orphan invoice. Do not remove the constraint to make the error go away.

Level 11Designing tables

Why

Most hard queries are caused by bad tables. A good design makes queries simple and makes bad data impossible to store: no invoice without a vendor, no negative amount, no due date before the invoice date.

CREATE TABLE invoices (
  id             SERIAL PRIMARY KEY,                     -- auto-numbered
  invoice_no     TEXT NOT NULL,
  vendor_id      INT NOT NULL REFERENCES vendors(id),
  cost_center_id INT REFERENCES cost_centers(id),
  invoice_date   DATE NOT NULL,
  due_date       DATE NOT NULL,
  amount         NUMERIC(12,2) NOT NULL CHECK (amount > 0),
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (vendor_id, invoice_no),                       -- no duplicate billing
  CHECK  (due_date >= invoice_date)
);
ConstraintPrevents
PRIMARY KEYDuplicate or missing ids
NOT NULLMissing required values
UNIQUE (vendor_id, invoice_no)The same vendor invoice entered twice (a duplicate payment risk)
REFERENCES (foreign key)An invoice pointing to a vendor that does not exist
CHECKValues breaking a rule (negative amount, due before issued)

Foreign key options

When the referenced row is deleted, the foreign key decides what happens:

  • ON DELETE RESTRICT (the default behaviour): refuse the delete. Right for vendors and invoices, which you should never lose.
  • ON DELETE CASCADE: delete the child rows too. Right for invoice lines, which mean nothing without their invoice.
  • ON DELETE SET NULL: keep the child, clear the link. Possible for a cost centre that is closed.

Choosing types

Use NUMERIC(12,2) for money, never FLOAT or REAL: floats round, and 0.1 + 0.2 is not exactly 0.3. Use DATE for accounting dates and TIMESTAMPTZ for moments in time (when a row was created).

Normalisation in one sentence per form

  • 1NF: one value per cell. No "GL: 6100, 6200" lists in a column; use a separate table of invoice lines.
  • 2NF / 3NF: every column describes the key, the whole key, and nothing but the key. The vendor's country belongs in vendors, not repeated on every invoice.

Relationships

  • One-to-many: one vendor, many invoices. The foreign key goes on the "many" side (invoices.vendor_id).
  • Many-to-many: vendors ↔ cost centres allowed to buy from them. Use a junction table with two foreign keys and a primary key on both columns.
Design an invoice_lines table: each invoice has several lines, each with a GL account and an amount.
CREATE TABLE gl_accounts (
  code TEXT PRIMARY KEY,           -- e.g. '6100'
  name TEXT NOT NULL
);
CREATE TABLE invoice_lines (
  invoice_id INT REFERENCES invoices(id) ON DELETE CASCADE,
  line_no    INT,
  gl_code    TEXT NOT NULL REFERENCES gl_accounts(code),
  amount     NUMERIC(12,2) NOT NULL,
  PRIMARY KEY (invoice_id, line_no)
);
Design the approved-vendor list (which cost centres may buy from which vendors).
CREATE TABLE approved_vendors (
  vendor_id      INT REFERENCES vendors(id),
  cost_center_id INT REFERENCES cost_centers(id),
  approved_on    DATE NOT NULL DEFAULT CURRENT_DATE,
  PRIMARY KEY (vendor_id, cost_center_id)
);

Level 12Window functions

Why

GROUP BY collapses rows: you get the vendor total but lose the individual invoices. A window function computes over a group and keeps every row. Running totals, month-over-month change, share of total and rankings are all window functions, and they are a favourite topic in finance and data interviews.

SELECT id, vendor_id, invoice_date, amount,
  SUM(amount) OVER (ORDER BY invoice_date)   AS running_total,
  SUM(amount) OVER (PARTITION BY vendor_id) AS vendor_total,
  RANK() OVER (PARTITION BY vendor_id ORDER BY amount DESC) AS rnk
FROM invoices;

PARTITION BY = "per group" (like GROUP BY, but without collapsing). ORDER BY inside OVER = "in what sequence", which you need for running totals and ranks.

Month-over-month change with LAG

WITH monthly AS (
  SELECT DATE_TRUNC('month', invoice_date)::date AS month,
         SUM(amount) AS spend
  FROM invoices GROUP BY 1
)
SELECT month, spend,
       spend - LAG(spend) OVER (ORDER BY month) AS change
FROM monthly ORDER BY month;
-- Jan 12000 (–) · Feb 4500 (−7500) · Mar 12500 (+8000) · Apr 15950 (+3450)

The classic: top N per group

WITH ranked AS (
  SELECT id, vendor_id, amount,
         ROW_NUMBER() OVER (PARTITION BY vendor_id
                            ORDER BY amount DESC, id) AS rn
  FROM invoices
)
SELECT * FROM ranked WHERE rn = 1;   -- largest invoice per vendor

You cannot write WHERE rn = 1 in the same query, because WHERE runs before window functions are computed. That is why the CTE is needed.

Each vendor's share of total spend, in %.
SELECT v.name, SUM(i.amount) AS spend,
  ROUND(100 * SUM(i.amount) / SUM(SUM(i.amount)) OVER (), 1) AS pct
FROM invoices i JOIN vendors v ON v.id = i.vendor_id
GROUP BY v.name
ORDER BY spend DESC;

Atlas 60.1% · Nordic 20.0% · Lumen 17.8% · Gulf 2.1%. SUM(SUM(x)) OVER () = the grand total of the grouped sums.

Cumulative amount paid on invoice 106, payment by payment.
SELECT id, paid_on, amount,
  SUM(amount) OVER (ORDER BY paid_on) AS paid_to_date
FROM payments
WHERE invoice_id = 106;

5000, then 7500.

Level 13Indexes and transactions

Indexes

Why

Without an index, WHERE vendor_id = 2 reads every row (a "sequential scan"). An index works like a book's index: a sorted lookup that jumps straight to the matching rows. On ten million invoice lines, that can take a month-end query from minutes to milliseconds.

CREATE INDEX idx_invoices_vendor   ON invoices (vendor_id);
CREATE INDEX idx_payments_invoice  ON payments (invoice_id);
CREATE INDEX idx_invoices_vendor_date ON invoices (vendor_id, invoice_date);

EXPLAIN ANALYZE
SELECT * FROM invoices WHERE vendor_id = 2;
  • Index the columns you filter on, join on and sort by. PostgreSQL does not automatically index foreign key columns, so index them yourself.
  • In a multi-column index, order matters. (vendor_id, invoice_date) helps queries that filter by vendor, but not queries that filter by date alone.
  • Indexes cost something: writes get slower and they use disk space. Add them when EXPLAIN shows a slow scan, not "just in case".
  • WHERE UPPER(name) = … or LIKE '%x' cannot use a normal index.

Transactions

Why

Paying an invoice means two changes: money leaves the bank account, and a payment row is recorded. If the second step fails, the first must be undone too, or the books no longer balance. A transaction makes a group of statements all-or-nothing.

BEGIN;
UPDATE bank_accounts SET balance = balance - 4500 WHERE id = 1;
INSERT INTO payments VALUES (6, 103, '2024-07-01', 4500);
COMMIT;   -- any error before this → ROLLBACK
-- (bank_accounts is an imaginary table, for illustration)

Transactions guarantee ACID: Atomic (all or nothing), Consistent (the constraints always hold), Isolated (other sessions don't see your half-finished work), and Durable (once committed, the data survives a crash). It is the same idea as a journal entry whose debits must equal its credits before it can be posted.
