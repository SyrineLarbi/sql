01 SELECT: read data

SELECT * FROM invoices;           -- all columns
SELECT id, amount FROM invoices;
SELECT id, amount * 0.20 AS vat
FROM invoices;                    -- compute + rename
SELECT DISTINCT country FROM vendors; -- unique values
In real queries, list the columns you need instead of SELECT *. The query is faster, and it does not break when someone adds a column.

02 WHERE: filter rows

SELECT id, amount FROM invoices
WHERE amount > 5000 AND vendor_id = 1;

03 ORDER BY · LIMIT

SELECT id, amount FROM invoices
ORDER BY amount DESC, id
LIMIT 3 OFFSET 0;   -- 3 largest; OFFSET skips rows

ASC (smallest first) is the default. Without ORDER BY, the database can return rows in any order.

Postgres sorts NULLs last in ASC order. To change that: ORDER BY cost_center_id NULLS FIRST.

04 Aggregates: many rows → one

SELECT COUNT(*)               AS invoices,      -- 6
       COUNT(cost_center_id)  AS coded,         -- 5
       COUNT(DISTINCT vendor_id) AS vendors,     -- 4
       SUM(amount)             AS total,         -- 44950
       ROUND(AVG(amount), 2)   AS avg_invoice,   -- 7491.67
       MAX(amount), MIN(invoice_date)
FROM invoices;

COUNT(*) counts rows. COUNT(col) counts the values that are not NULL. COUNT(DISTINCT col) counts the unique values.

05 GROUP BY · HAVING

SELECT vendor_id, COUNT(*) AS n, SUM(amount) AS spend
FROM invoices
WHERE invoice_date >= '2024-01-01'  -- filters ROWS
GROUP BY vendor_id
HAVING SUM(amount) > 5000;          -- filters GROUPS
Every column in SELECT must either appear in GROUP BY or sit inside an aggregate. SELECT vendor_id, due_date … GROUP BY vendor_id is an error.

06 JOINs: follow the foreign keys

SELECT i.id, v.name AS vendor, c.name AS cost_center, i.amount
FROM invoices i
JOIN vendors v           ON v.id = i.vendor_id        -- FK → PK
LEFT JOIN cost_centers c  ON c.id = i.cost_center_id;  -- i, v, c = aliases

Every ON clause follows a foreign key to the primary key it points to. Here is what each join type returns for invoices ⟷ cost_centers:

TypeKeepsRows with the sample data
INNER JOIN (or JOIN)Only the rows that match on both sides5. Invoice 105 is dropped (no cost centre).

-- vendors with no invoices (the "anti-join")
SELECT v.name FROM vendors v
LEFT JOIN invoices i ON i.vendor_id = v.id
WHERE i.id IS NULL;                 -- → Orbit Consulting

-- self join: cost centre → parent
SELECT c.name, p.name AS parent
FROM cost_centers c
LEFT JOIN cost_centers p ON p.id = c.parent_id;
In a LEFT JOIN, a filter on the right table belongs in ON, not in WHERE. A WHERE filter on the right table throws away the NULL rows, so the query behaves like an INNER JOIN.
Joining invoices to payments repeats invoice 106 (it has 2 payments). SUM(i.amount) after that join gives 59 950 instead of 44 950. Sum payments per invoice in a CTE first, then join (card 07).

07 Subqueries · CTEs

-- invoices above the average invoice
SELECT id, amount FROM invoices
WHERE amount > (SELECT AVG(amount) FROM invoices);

-- invoices with no payment at all
SELECT id FROM invoices i
WHERE NOT EXISTS (SELECT 1 FROM payments p
                  WHERE p.invoice_id = i.id);  -- 103, 105

-- CTE: open balance per invoice, no double counting
WITH paid AS (
  SELECT invoice_id, SUM(amount) AS paid
  FROM payments GROUP BY invoice_id
)
SELECT i.id, i.amount,
       i.amount - COALESCE(p.paid, 0) AS open_balance
FROM invoices i
LEFT JOIN paid p ON p.invoice_id = i.id;

08 CASE: if / else

SELECT id, amount,
  CASE
    WHEN amount >= 10000 THEN 'CFO approval'
    WHEN amount >= 5000  THEN 'manager approval'
    ELSE 'auto-approve'
  END AS approval
FROM invoices;

-- conditional totals (pivot)
SELECT SUM(amount) FILTER (WHERE vendor_id = 1) AS atlas,
       SUM(CASE WHEN vendor_id = 2 THEN amount ELSE 0 END) AS nordic
FROM invoices;

Conditions are checked from top to bottom, and the first match wins.

09 NULL: "unknown"

WHERE cost_center_id IS NULL
WHERE cost_center_id IS NOT NULL
COALESCE(paid, 0)          -- first non-NULL value
NULLIF(budget, 0)         -- NULL if budget = 0 (avoids ÷0)
  • NULL = NULL gives NULL, not true.
  • 12000 - NULL gives NULL, so an unpaid invoice's balance comes out NULL unless you COALESCE the payment to 0.
  • Aggregates (except COUNT(*)) ignore NULLs.
  • NOT IN (…) on a list that contains a NULL returns no rows. Use NOT EXISTS instead.

11 Window functions

SELECT id, vendor_id, invoice_date, amount,
  SUM(amount) OVER (ORDER BY invoice_date)   AS running_total,
  SUM(amount) OVER (PARTITION BY vendor_id) AS vendor_total,
  RANK() OVER (PARTITION BY vendor_id
                ORDER BY amount DESC) AS rank_in_vendor
FROM invoices;

Like GROUP BY, but every row is kept, and the group result is added as a new column.

ROW_NUMBER gives 1,2,3,4 · RANK gives 1,1,3 · DENSE_RANK gives 1,1,2 · LAG/LEAD read the previous/next row (month-over-month change).

12 Finance recipes

-- AP aging as of a fixed date (use CURRENT_DATE in real life)
WITH paid AS (
  SELECT invoice_id, SUM(amount) AS paid FROM payments GROUP BY invoice_id
), open_items AS (
  SELECT i.id, i.due_date, i.amount - COALESCE(p.paid, 0) AS open_balance
  FROM invoices i LEFT JOIN paid p ON p.invoice_id = i.id
)
SELECT CASE
         WHEN DATE '2024-06-30' - due_date <= 0  THEN 'not due'
         WHEN DATE '2024-06-30' - due_date <= 30 THEN '1-30'
         WHEN DATE '2024-06-30' - due_date <= 60 THEN '31-60'
         WHEN DATE '2024-06-30' - due_date <= 90 THEN '61-90'
         ELSE '90+'
       END AS bucket,
       COUNT(*) AS invoices, SUM(open_balance) AS open_amount
FROM open_items
WHERE open_balance > 0
GROUP BY bucket ORDER BY bucket;
-- 31-60: 2 invoices, 8450 · 61-90: 1, 5000 · 90+: 1, 4500

-- monthly spend and month-over-month change
WITH monthly AS (
  SELECT DATE_TRUNC('month', invoice_date)::date AS month, SUM(amount) AS spend
  FROM invoices GROUP BY 1
)
SELECT month, spend, spend - LAG(spend) OVER (ORDER BY month) AS change
FROM monthly ORDER BY month;

-- late payments (paid after the due date)
SELECT p.invoice_id, i.due_date, p.paid_on, p.paid_on - i.due_date AS days_late
FROM payments p JOIN invoices i ON i.id = p.invoice_id
WHERE p.paid_on > i.due_date;     -- 102 (3 days), 106 (21 days)

13 INSERT · UPDATE · DELETE

INSERT INTO vendors (id, name, country)
VALUES (6, 'Delta Print', 'Spain');

UPDATE invoices
SET cost_center_id = 3
WHERE id = 105;

DELETE FROM vendors WHERE id = 6;

-- Postgres: see what changed
UPDATE invoices SET due_date = due_date + 15
WHERE id = 103 RETURNING *;
An UPDATE or DELETE without WHERE changes every row in the table. Run the same WHERE as a SELECT first and check which rows come back.

14 CREATE TABLE · foreign keys · index

CREATE TABLE vendors (
  id      INT PRIMARY KEY,
  name    TEXT NOT NULL UNIQUE,
  country TEXT
);
CREATE TABLE invoices (
  id             INT PRIMARY KEY,
  vendor_id      INT NOT NULL REFERENCES vendors(id),
  cost_center_id INT REFERENCES cost_centers(id),
  invoice_date   DATE NOT NULL,
  due_date       DATE NOT NULL,
  amount         NUMERIC(12,2) NOT NULL CHECK (amount > 0),
  CHECK (due_date >= invoice_date)
);
CREATE INDEX idx_invoices_vendor ON invoices(vendor_id);
ALTER TABLE vendors ADD COLUMN iban TEXT;
DROP TABLE old_table;    -- permanent!

Primary key: identifies each row and can never repeat. Foreign key (REFERENCES): the value must exist in the other table, so an invoice can never point to a vendor that does not exist.

Store money as NUMERIC, never FLOAT/REAL. Floats round: 0.1 + 0.2 is not exactly 0.3.

15 Transactions: all or nothing

BEGIN;
UPDATE bank_accounts SET balance = balance - 4500 WHERE id = 1;
INSERT INTO payments VALUES (6, 103, '2024-07-01', 4500);
COMMIT;      -- or ROLLBACK; to undo both

If anything fails between BEGIN and COMMIT, ROLLBACK puts the data back exactly as it was. Money never leaves the bank without the payment being recorded. (bank_accounts is an imaginary table for this example.)

16 The order SQL really runs in

You write SELECT first, but the database runs the clauses in this order:

  1. FROM / JOIN
  2. WHERE
  3. GROUP BY
  4. HAVING
  5. SELECT
  6. DISTINCT
  7. ORDER BY
  8. LIMIT

This order explains why a column alias from SELECT cannot be used in WHERE, and why it can be used in ORDER BY.
